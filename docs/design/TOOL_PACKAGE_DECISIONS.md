## 0. この文書の役割

### 保存ツール一覧・再登録・完全削除と版選択(確定・2026-09-07)

依頼者の指示で「前の版へ戻す」を手入力から読み取り専用のドロップダウンへ変更する。
一覧の旧版行から押した場合も、その版を初期選択した確認画面を出す。

- 「保存済みのツール」には、台帳に登録が無くPCに残っているツールを別一覧で表示する。
  登録中・無効化中のツールは対象外。ファイルを置いただけで稼働中モデルとしては表示しない。
- **再登録**: 行を1件選択し、保存原本のある版をドロップダウンで指定する。
  元ZIPを選び直す必要はない。保存版照合と通常の受入検査を全て通し、未承認から再登録する。
- **完全削除**: 初期状態では全て未チェック。チェックしたツールの名前・ID・全保存版を確認してから、
  そのツールの保存原本・展開物・生成物だけを削除する。USBの元ZIP・業務の入力/出力・診断ログは対象外。
  元に戻せず、再登録には元ZIPか外部バックアップが必要であることを確認画面に明記する。
- 再登録・完全削除の直前にも、管理ロック内で台帳と確認時の保存状態を照合する。
  削除では全選択を先に検査し、稼働中のハブとOpen WebUIに登録が無いことも確認する。
  サービスを確認できない場合や処理中は削除しない。削除完了まで実行ロックも保持する。
  絶対パスの範囲・全階層のリンクを検査し、外部を辿る削除は拒否する。
- ファイル削除に失敗した場合は、既に消えた対象と中止理由を報告し、以降の削除を止める。
  「元へ戻した」「全て削除できた」と偽って表示しない。自動削除は導入しない。

実装: `tools/toolpack/toolpack_saved.py` / `toolpack_dialogs.py` / `toolpack_manage.py` / `toolpack_gui.py`。
試験: `tools/tests/toolpack/test_toolpack_saved.py`(架空ファイル・仮の登録先・非表示の実Tk画面)。

### 再追加時の明示確認と新版採番(確定・2026-09-06)

依頼者の指示で、同じIDの登録・保存済みの版を見つけた場合は、追加・入れ替えの
実行前に「保存済みの版を使う / 今回のZIPを新版として登録する / キャンセル」を確認する。
登録の無い保存ファイルも確認画面に版一覧として表示し、登録済みとは区別する。

- **新版番号は管理画面で指定する**(依頼者が明示選択)。保存済みの全ての版より大きく、持ち込み版以上の番号のみ。
  変更は `tool.json` の版番号とmanifestだけ。業務コード・元の持ち込みZIP・既存版は変更しない。
  梱包器・検証器を再利用し、採番後の単体テスト・サンプル実行も省略しない。
  新版の `source/package.localtool` は実行内容と一致する採番済みZIP、
  `source/imported.zip` は持ち込み原本。install.jsonへ原本ハッシュ・元版番号・採番元を記録する。
- **登録を外した保存版は明示選択時だけ再登録する。** 保存原本・設置時ハッシュ・展開物の全数一致を
  確認してから通常の検査を通す。本体・原本を上書きせず、承認は未承認から。
  登録済みの旧版への切替・有効化は既存の管理コアへ委譲し、承認済み保護を迂回しない。
- **確認の間にZIP・台帳が変わったら再選択。** 実行時も管理ロック内で状態・版の衝突を検査する。
  キャンセルで登録は変えず、再登録失敗時にも既存の保存ファイルを削除しない。
- 同じ版番号で内容を上書きすることは引き続き禁止。新版の採番はこの規則の迂回ではなく、
  利用者が指定した**別の版**の作成であり、無断で番号を変更しない。

実装: `tools/toolpack/toolpack_selection.py` / `toolpack_install.py` / `toolpack_gui.py`。
回帰試験: `tools/tests/toolpack/test_toolpack_reinstall.py`。

### 追加ツール制作の納品経路(確定・2026-09-06)

依頼者の指示で、短い機能説明からオンラインAIが `.zip` を作って渡す経路を標準とする。
GitHubは規格と既存コードの参照元。利用者は完成ファイルをUSB等で運び、管理GUIから追加する。
オンラインAIは既存本体へOpen WebUI Tool/Pipeを足さず、独立パッケージを制作・検査・梱包する。
PR作成・push・マージ・本番登録は別途明示的に依頼された場合のみ。
この制作経路では、以下の共同保守向けの「コミット・push local」規則を提出義務と解釈しない。
従来SPEC第7章の「PRを出し、院内担当者が固める」はこの方針と矛盾するため廃止した。

院内PCを完全にオフライン化した後も、新しい業務ツールを追加できる状態を作りたい。
その仕組みを決めていく過程で、**提案と決定が混ざって認識がずれた**ため、この台帳を置く。

読み方:

| 欄 | 意味 | 扱い |
|---|---|---|
| **確定** | 依頼者が決めたこと | 前提として使ってよい |
| **推奨(未決)** | 誰かの提案。まだ決まっていない | 実装の根拠にしない。提案元を併記する |
| **決定待ち** | これから決めること | 決めるために要る材料を書いてある |
| **判明している事実** | 実コードを読んで確認したこと | 判断材料。事実なので動かない |

オンラインのAI(ChatGPT / Codex / Claude 等)がこのリポジトリを読む場合、
**この文書の「推奨(未決)」に従って実装してはいけない。**

### 複数のAIで共有するための決まり

この構想は、オンラインの GPT・Claude と院内の Kilo が並行して検討している。
**認識がずれる原因は、各自が会話の中に自分の要約を持つことである。**
実際、公開範囲の方針を変えたとき、この文書の3箇所に古い前提が残り、
GPT の指摘で見つかった(第9章)。それを防ぐため、次を決める。

1. **共通台帳はこのファイル1枚だけ。** 会話の要約と食い違ったら、**Git上の現在の台帳**が正しい
2. 作業を始めるときは、**台帳・現在のブランチ・Gitの状態を読み直す**。会話の途中からでも同じ
3. **「未決」を勝手に「確定」へ移さない。** 移せるのは依頼者が明示的に決めたときだけ
4. 「推奨」には**提案元**(Claude / GPT / Codex / 依頼者)を必ず書く
5. 変更したら**変更履歴へ1行足す**。指摘を受けて直したなら指摘元も書く
6. 実装中に文書と違う事実が見つかったら、第5章へ**事実として積む**(推測は積まない)
7. **同時に書き換えない。固定の書き手は置かない。**
   その時点で作業を担当しているAIだけが編集し、他は内容確認に回る。
   未コミットの変更が残っている間は、別のAIは編集しない
8. **編集したら、テスト・コミット・`push local` まで終えてから担当を離れる**
9. 方針を変えたら、**その前提に依存していた記述を必ず洗う**。
   1箇所直して終わりにしない(3箇所の消し残しはこれで起きた)

## 1. 目的(確定)

**院内PCを完全にインターネットから遮断した後も、開発担当者がいない状態で、
利用者自身が新しい業務ツールを追加できるようにする。**

そのために、オンラインAIには決められた形式のツールを作らせ、
院内PC側には、その形式を機械的に検査して自動接続するWindowsアプリを用意する。

利用者に Python・FastAPI・ハブ・Pipe・Open WebUI の管理方法を理解させない。

## 2. 確定していること

### 2-1. 全体の流れ

```
【インターネット側】
GitHub(現システムのコード)
  ↓ 読む
ChatGPT / Codex / Claude
  ↓ 決められた形式で作る
追加ツールのパッケージ
  ↓
USB等へ保存

【完全オフラインの院内PC】
Windows接続アプリでパッケージを選ぶ
  ↓ 検査
ツールハブへ接続
  ↓ Pipeを用意して localhost:3000 へ登録
Open WebUI のモデル一覧に独立したモデルとして表示
```

### 2-2. 役割

| 要素 | 役割 | 役割でないもの |
|---|---|---|
| GitHub | オンラインAIに現システムを正確に理解させる | **院内PCへの配布経路ではない**。院内PCは接続・同期・更新確認を一切しない |
| オンラインAI | 業務処理本体を作る | — |
| USB等 | パッケージを運ぶ | Git履歴は運ばない |
| Windows接続アプリ | 検査・接続・登録・自己診断・ロールバック | ツールを作らない |
| ツールハブ(8010) | 共通の受付・実行・返却 | 業務ロジックを持たない |
| Open WebUI | 利用者の入口 | — |

### 2-3. 決まっている方針

- 院内PCは完全オフライン。GitHubへ接続しない
- **追加ツールごとにPipeを1本作り、Open WebUI のモデル一覧へ独立したモデルとして表示する**
- 登録は `localhost:3000` に対して行う(インターネット不要)
- **登録はいちばん最後に行う。** 展開・形式検査・安全性検査・スモークテスト・ハブ接続確認を
  すべて終えてから Open WebUI へ登録する
- **登録後に失敗した場合も完全に取り消す。** 「注意表示だけで残す」は採らない
- 失敗を成功として扱わない。中途半端な変更を残さない
  (正確には「既存環境を変更しない」ではなく「**変更前の状態へ確実に戻す**」)
- 実データ・個人情報・実物テンプレート・接続情報を GitHub へ載せない
- `input/` の原本を上書きしない
- 業務ロジックをハブへ重複実装しない。処理本体の唯一性を守る
- 本文や氏名を運用ログへ残さない
- 追加に失敗しても既存ツールを壊さない
- オフライン環境で再現・検証できること
- **独立したファイルまたはフォルダを追加するだけで、Pipeとして登録できる仕組みが要る。**
  既存のモデルを編集して機能を足すのではなく、別モデルとして増やせるようにする
  (ひな型違い・文体違いの派生も、既存を書き換えず別モデルとして足す)
- **既存Pipe(文章処理・Excel分析・使い方ヘルプ)も、追加ツールと同じGUIで一覧管理する。**
  追加専用のインストーラではなく、院内モデルの管理アプリにする
- **正式なモデルとして運用するか、個人製作の非認証モデルとして扱うかを分ける**(経営企画課の方針)
- **認証には企画課内で2名以上の承認が要る**(同上)。
  現状の対策はモデル名を変えるだけなので、仕組みとして持たせる
- **未承認モデルも全員に見せる。** 見えなくするのではなく、
  未承認であることが**見て分かる**ようにする

### 2-4. 自動追加の対象にしないもの(システム本体の更新として扱う)

常駐サービスの追加 / 管理者権限 / Windowsへのソフトインストール /
コアコードの変更 / 独自画面 / 外部インターネット接続 / 院内に無いライブラリ /
GUI操作・Office COM

> **注**: 「既存 `tools/` を呼ぶもの」をここへ入れるかは**未決**(D-7 を参照)。

## 3. 設計判断の項目

順序に意味がある。上の決定が下を縛る。

### D-1. 所定形式による固定接続(確定:A方式)

**確定**: 所定形式のパッケージだけを、Windows管理アプリが決められた手順で
検査・接続する。接続経路にAIの判断を挟まず、Qwenが動かなくても追加できる構造にする。

**補足(重要)**: 固定接続を選んでも、Qwenの補助利用を捨てることにはならない。
将来必要になれば、Qwenは
「規格外のツールを読んで **A形式のパッケージへの変換案(下書き)を出す**、
採用するかは人が決める」という補助として足せる。
判定にも接続にも関与しないため、「合否をQwenに判断させない」原則を保ったままBの価値を拾える。
どこまで補助機能を付けるかはD-6で決める。

---

### D-2. 持ち込む単位(確定:`.zip` 1ファイル、旧 `.localtool` も受入可)

**確定**(2026-09-06依頼者変更。検算はD-4の表を参照): 普通の `.zip` **1ファイル**を標準出力とする。
管理GUIは `.zip` と旧 `.localtool` の両方を選択でき、同一の検査を通す。
既存原本の内部保存名 `package.localtool` は互換性のため維持する。既存の登録・履歴の移行は不要。
過去の変更履歴や構成例にある `.localtool` の記述は旧形式を指す。
中身は `tool.json` / `main.py` / `manifest.sha256` / `tests/` / `samples/` / `resources/` / `README.md`。

**検査の規約(確定)**:

- **展開前にエントリ名を検査する**: 絶対パス / ドライブ文字 / `..` / Windows予約名(`CON`・`NUL`・`COM1` 等)/
  パス長 / **重複エントリ** / **Windowsで同一になる大文字小文字違い** / **末尾の空白・ピリオド** /
  **コロン(代替データストリーム)** / **暗号化エントリ** / **ZIP内のシンボリックリンク・特殊ファイル** /
  **正規化後のパス衝突**。`extractall` に頼らず、検証済みの名前を1件ずつ自前の結合先へ展開する
- 展開前に**非圧縮サイズ合計と件数の上限**を確認する(ZIP爆弾対策)。
  初期上限: **エントリ500件・1ファイル100MB・非圧縮合計200MB**。
  上限は名前付き定数にしてテストの対象にする
- **パッケージ内のパスはASCII限定**。ZIPのファイル名エンコーディングは作成側実装に依存し、
  日本語名は化ける(日本語はファイルの中身には自由に使える)
- ZIPのCRCで分かるのは**転送の健全性**だけ。**内容の完全性**(欠け・余り)は
  `manifest.sha256` の全列挙と突合して確かめる。
  **`manifest.sha256` 自身は照合一覧の対象外**(自分自身をハッシュ化できない)。
  それ以外の通常ファイルは**すべて列挙必須**とし、一覧に無いファイルは「余り」として拒否する

原本 `.localtool` の保管は D-3 の構成に含む。

以下は検討時の比較(経緯として残す):

| 選択肢 | 成立するか | 備考 |
|---|---|---|
| 単体 `.py` | 技術的には可能 | `--self-test` / `--describe` を持たせれば検査できる。ただしテスト・サンプル・READMEを別ファイルで持てず、人が確認しにくい |
| 決められた構成のフォルダ | 成立する | 完全性の検査は manifest の列挙と突合で行う |
| フォルダをZIP化(`.localtool` 等) | 成立する | 転送の健全性はZIPのCRCで分かる |

**判断の基準になる区別**:

- **転送の健全性**(壊れていないか) — ZIPなら形式で検出できる
- **内容の完全性**(必要なファイルが揃っているか) — **ZIPでも検出できない**。
  manifest に全ファイルを列挙し、欠けも余りも突合するしかない

つまり**どの形式でも manifest の突合は必須**であり、ZIP は転送の健全性を1つ肩代わりするだけである。

### D-3. 追加ツール専用の保存領域(確定)

**確定**(2026-08-31): **リポジトリ内**のGit管理外専用領域に置き、`.gitignore` へ `additional-tools/` を追加する。

リポジトリ内に置く理由: [hub.py](../../local_tool_bridge/hub.py)・[doctor.py](../../tools/doctor.py)・
[start_local_services.py](../../tools/start_local_services.py) のパス解決がすべて `ROOT`
(`Path(__file__).resolve().parents[1]`)基準で、リポジトリ内なら追加設定が一切要らない。
`work/` `output/` `logs/` が既に「リポジトリ内・Git管理外の実行時領域」として同じ形で運用されている。

**確定した構成**(原本・展開物・生成物を分ける。manifestの照合対象を `package/` に閉じるため):

```
additional-tools/
├─ incoming/                       USBから複製した .localtool(検査待ち)
├─ staging/                        展開・検査中(終了時に削除)
├─ installed/<tool_id>/<version>/
│   ├─ source/package.localtool    原本(再検査・ロールバックの単位)
│   ├─ package/                    展開物(tool.json / main.py / manifest.sha256 / tests/ / samples/ / resources/)
│   ├─ generated/open_webui_<tool_id>_pipe.py
│   └─ install.json                この版のインストール記録(日時・ハッシュ・検査結果)
├─ rejected/                       診断結果のみ(.localtoolも展開ツリーも残さない)
└─ registry/
    ├─ registry.json               有効版の正本。唯一の有効化スイッチ
    └─ approvals.json              承認記録(運用ログと分離)
```

**確定した規約**:

- **`registry.json` だけが有効版の正本。** ディレクトリが置いてあることは有効化を意味しない。
  これにより staging → installed の移動は同一ボリューム内の `os.rename` で足り、
  途中で落ちても registry 未更新なら不活性なゴミが残るだけで既存環境は壊れない。
  registry の書き換えは一時ファイルへ書いて `os.replace`(NTFS同一ボリュームで原子的)
- **成功後は `incoming/` と `staging/` を削除する**
- **失敗時は危険なパッケージを常駐させない。** rejected/ には**個人情報を含まない診断結果だけ**を残し、
  失敗した `.localtool` の院内PC側コピーは削除する(原本は持ち込み元のUSB側に残っている)
- **`installed/` 内で registry の有効版になっていないディレクトリを自動削除しない**
  (将来のロールバック用の版まで消えるため)。自動掃除は `staging/` の未完了物だけ。
  孤立版・旧版は doctor が**報告するだけ**にする。削除の扱いは D-10 の確定後に決める
- **`source/package.localtool` は版ごとに保存する**(再検査・ロールバックの単位)。
  ただし**同じPC内の保管はバックアップではない**。PC・ディスク故障には耐えないため、
  外部媒体へのバックアップは別機能として扱う(D-17)
- **ハブは追加ツールの `main.py` を直接実行しない。**
  環境変数・読み書き・通信を制限する追加ツール専用ランナーを必ず通す(制限の中身は D-9 で固める)

**未決**: rejected/ の保持期限(D-10 と合わせて決める)。

### D-5. 固定の起動・返却契約(確定:request.json 方式)

**原則(確定)**: manifest は**外側の契約だけ**を宣言し、業務判断は処理本体の中で行う。
接続アプリは業務内容を理解せず、契約遵守と安全性だけを検査する。

**起動(確定)**: 引数は `--request` の1つだけ。実行は必ず専用ランナー経由(D-3・D-9)。

```
<venv python> <ランナー> …制限オプション… -- main.py --request <ジョブ内の request.json>
```

```jsonc
{
  "contract": 1,
  "instruction": "利用者の依頼文そのまま(ハブ側で最大10,000字)",
  "inputs": [
    { "id": "in-1", "role": null, "path": "in/in-1_4月実績.xlsx", "filename": "4月実績.xlsx" }
  ],
  "outdir": "out",
  "config": {}
}
```

- **`path`・`outdir` はジョブフォルダ基準の相対パス**。PCの絶対パスを渡さない
- **各入力は固有の `id` を持ち、内部保存名は `id` 基準にする。**
  同名ファイルを2件渡しても上書きされない
- **役割の判定根拠は `role` だけ。** 順序や元ファイル名を役割の根拠にしない。
  role を使わない初期ツールでは null でよい
- `config` は D-13(設定だけのパッケージ)の注入口。初期版は空
- **添付ファイルの読み取りはコアが持つ(確定・2026-08-31 追加)**。
  ランナーが `toolpack_textio` をジョブ直下へ複製し、パッケージは
  `import toolpack_textio` の1行で使う。**パッケージに自前の open を書かせない。**
  - 理由: 利用者が持ってくる形式は `.txt` に限らない(実測で文字起こしは全件 `.docx`。5-20)。
    形式ごとの読み方をツールの数だけ書かせると、対応も修正も散らばる
  - 置き場所がジョブ直下なのは、**読めるが書けない**領域だから。
    ツール側から差し替えられない。`sys.path` もコア側を先に置く
  - 解析はツール本体と同じ隔離の中で走る。**親プロセスでは開かない**
  - ファイルの中身そのもの(Excelの書式など)が要るツールは、
    これを使わず `path` を直接開いてよい(例: Excel比較グラフ)
- CLI引数方式(`--input`/`--instruction`/`--outdir`)を採らない理由:
  複数入力・役割・設定の追加が引数体系の破壊的変更になる。
  request.json ならフィールド追加で済み、テストもスモークも
  「request.json を書いて呼ぶ」だけで再現できる

**返却(確定)**: 標準出力へJSON1行のみ。

```json
{ "status": "ok", "message": "…", "files": ["比較グラフ.png"], "skipped": [], "notes": [] }
```

| 区分 | 表現 | ハブでの扱い |
|---|---|---|
| 成功 | exit 0 + `"status": "ok"`(skipped空) | 通常応答 |
| 要確認あり成功 | exit 0 + `"ok"` + `skipped` に要確認項目 | 既存 `RunResult.skipped` と1対1 |
| 利用者エラー(利用者が直せるもの) | exit 0 + `"user_error"` + 対処を書いた `message` | ローダが `ValueError` へ変換 → [app.py](../../local_tool_bridge/app.py) の既存 `except ValueError → 422` に乗り、チャットへ出る |
| ツール内部エラー | **exit ≠ 0 またはJSON不正**(JSONの状態値ではない) | ローダが内部エラーとして処理(下記ログ規約) |

- `skipped` は**利用者の対処が要るもの**、`notes` は**対処が要らない補足**
  (既存 `RunResult` の規約と同一。混ぜると成功が失敗に見える)
- **`files` は `outdir` 基準の相対パスとし、ローダが検証する(確定)**:
  通常ファイルであること / 許可拡張子 / 個数 / サイズ / 解決後が `outdir` 配下であること
- **本文引用の線引き(確定)**: 成功時の `message` には必要最小限の本文引用を許可する
  (診断系ツールに必要)。ただし**運用ログ・失敗ログには本文・氏名・元ファイル名を残さない**
- **失敗時の stdout / stderr をそのまま運用ログへ保存しない(確定)。**
  既存 `run_repo_script` の「失敗時に末尾4000文字を例外へ載せる」挙動を追加ツールへは流用せず、
  利用者へは個人情報を含まないエラーコードと対処を返す。
  失敗の詳細をデバッグ用にどこへどこまで残すかは**未決**(D-9・実装設計で決める)

**確定した運用値**:

- `timeout_seconds`: **既定300秒・上限1500秒**(ハブの1800秒より内側)。検証器が強制する
- **Ollama を使うツールは、登録前のスモークで実際の Ollama を使って確認する。**
  利用中ジョブとの競合(`_RUN_LOCK`・5-7)を避ける方法は D-9・実装設計に残す

**tool.json の宣言項目(確定。D-7 の3ツール検算で不足が無いことを確認)**:

`schema_version` / `id` / `version` / `display_name`(【未承認】接頭辞はインストーラが付ける。
パッケージには書かせない)/ `summary` / `inputs{accepts, min, max}` /
`outputs{produces, may_be_empty}` / `requires{core_api, packages, models}` /
`permissions{ollama}` / `timeout_seconds` /
`routing{label, patterns, examples, suggestions}` / `smoke{make_sample, request, expect}`

**role の設定者(確定・2026-08-31追記)**: Open WebUI の添付には役割のメタデータが無いため、
役割を決められるのは利用者しかいない。

- 複数入力で役割が要るツールは、`tool.json` へ **必要な role 名と利用者向け表示名を宣言**する
- Pipe が role を設定してよい根拠は次の2つ**だけ**:
  1. 利用者の明示指定(例:「基準:『4月実績』 比較:『5月実績』」。正規表現で読む)
  2. 不足時に Pipe が添付一覧を番号付きで示し、利用者が**番号で明示的に選んだ**回答
- **添付順から自動推測しない。** ファイル名は、利用者が明示的に名指ししたファイルとの照合にだけ使う

### D-9. 追加ツールの安全な実行方法(確定)

**正式方式(確定)**: 次の4つの組み合わせ。

1. **Python監査フック**による読み取り許可リスト・書き込み許可リスト・通信制限・子プロセス制限・
   **リンク作成の遮断**(`os.link` / `os.symlink` / `_winapi.CreateJunction`。発火は実測確認済み 5-13)。
   **フックは子プロセスの中で有効にする**: Git管理された固定ブートストラップ
   (パッケージ側から置換できない)が最初にフックを登録し、その後で `main.py` を読み込む。
   **親ランナーのフックでは子プロセスを監視できない**(監査フックはプロセス単位)
2. **最小環境変数**を新規に作って渡す(APIキー・トークン・`USERPROFILE` 系を渡さない。
   TEMP/TMP・`MPLCONFIGDIR` はジョブ内へ向ける。この構成で matplotlib が動くことは 5-14(d) で実測)
3. **Windowsジョブオブジェクト**(ctypesで実装。pywin32はwheelhouseに無い・5-13)による
   タイムアウト・メモリ上限・プロセス数制限・`KILL_ON_JOB_CLOSE` での**子プロセス全滅**
   (「プロセス数1」と venv リダイレクタの衝突、その回避は 5-14(c))
4. **制限トークン + 低整合性レベル**による、outdir外書込のOS強制

**1〜3は開発の第一段階、4は本番完成までの必須工程である。「将来、必要なら追加」ではない。**

| | 現行 [safe_task_runner.py](../../tools/safe_task_runner.py) | 追加ツール向け(確定) |
|---|---|---|
| 読み取り | 拒否リスト(`.env` / `data/` / `templates/`) | **許可リスト**: request.json / 渡された入力コピー / 自パッケージ配下 / 明示的に許可した共通資材 のみ |
| 書き込み | `work/` と `output/` | **今回専用の outdir・ジョブ内TEMP・`MPLCONFIGDIR` のみ**(`work/` も `output/` も外す) |
| 環境変数 | 素通し(親から継承) | 最小構成を新規作成。鍵・トークンを渡さない |
| 通信 | 全面禁止 | 既定は全面禁止。`permissions.ollama: true` のツールだけ `127.0.0.1:11434` を許可 |

**プロセス分離(確定)**:

```
接続アプリ
  ├─ 登録担当    : Open WebUI 管理APIキーを読む。追加ツールを実行しない
  └─ ツール実行担当: 管理APIキーを一切持たない。環境変数を最小構成で作り直す
```

**安全性の前提(確定・隠さないこと)**:

- 対象は**善意だが誤るオンラインAIのコード**と**偶発的な破損・改変**である
- **意図的に悪意あるパッケージは対応範囲外と明記する。** 監査フックを回避する
  Python(ctypes・ネイティブコードのI/O)を完全には封じ込めない
- **開発担当者不在が目的のため、人によるPRレビューを必須の最後の防御にはしない。**
  防御は 自動検査・実行隔離・manifest・持ち込み元の管理 で構成する
- 段階1では、管理APIキーファイルへのアクセスをOS権限では完全に遮断できず、
  **監査フックに依存する**。段階2(低整合性)でも読み取り隔離には限界が残る。
  **この事実を成功表示や設計文書で隠さない**

**検査対象コード(確定)**: `main.py` だけではない。実行される可能性のあるすべて —
`main.py` / それが import するパッケージ内Python / `samples/make_sample.py` /
テストコード / その他の実行可能物 — を検査し、**サンプル生成もテストも同じ専用ランナー内で実行する**。
**`.pyc` `.pyd` `.dll` `.exe` `.bat` `.cmd` `.ps1` `.pth` 等の同梱は初期版では禁止**(検証器が拒否)。

**リンク対策は二重(確定)**: 作らせない(監査フック)+ 返されても見抜く
(ローダが `files` の各パスを検証: 相対パス / 通常ファイル / 許可拡張子 / 個数 / サイズ /
`resolve()` 後が outdir 配下 / **`st_nlink > 1` のハードリンク拒否** / `Path.is_junction()` 検査)。
書き込み制限だけでは「読んで返す」持ち出し
(例: `{"files": ["../../data/名簿.xlsx"]}`)を防げないため、ローダ側の再検証は必須である。

**資源制限の初期値(確定)**: メモリ 2GB/ジョブ・プロセス数 1・出力ファイル最大20件・
出力合計最大200MB・timeout は D-5 どおり(既定300秒・上限1500秒)。
実ツール検査で不足が判明した場合だけ、この台帳上で見直す。

**Ollamaスモークの競合回避(確定)**: 現在の `_RUN_LOCK` は**ハブプロセス内の
`threading.Lock`** であり、別プロセスの管理アプリからは待てない。
ハブの通常ジョブと管理アプリのスモークが共有できる**プロセス間ロック
(Windows名前付きMutexまたはファイルロック)を一度だけ実装**し、
ハブの `_RUN_LOCK` をそれに置き換える。
管理アプリはロックの空きを待ち、GUIへ「現在の処理が終わるのを待っています」と表示する。
利用者の受付を強制停止する方式は初期版では採らない。

**失敗診断(確定)**: 保存先 `additional-tools/logs/`・保持期間14日(自動削除)。

| 記録するもの | 記録しないもの |
|---|---|
| 日時 / tool_id・version / パッケージハッシュ / 処理段階 / エラーコード / 禁止された操作の分類 / 終了コード / 所要時間と資源使用量 | 本文 / 氏名 / 元ファイル名 / 入力内容 / stdout・stderr の生データ / APIキーや環境変数の値 |

**禁止操作試験(確定)**: **本物の `data/`・`templates/`・`.env`・管理APIキーファイルを
試験対象にしない。** テスト専用の一時領域へ架空の秘密ファイルを作り、
それを読めないことを確認する(実装ミスがあっても実データへ届かない試験にする):

- `fake-data/patient.txt`
- `fake-home/admin_api_key.txt`
- `fake-project/.env`
- `fake-outside/secret.txt`

併せて、意図的に禁止処理を行う試験パッケージ群(コアツール読み・outdir外書込・
入力改変・子プロセス・LAN接続・未宣言Ollama接続・**ハードリンクを `files` で返す**・
`../` パス返却・JSON以外のstdout・無限ループ・メモリ大量確保・大量/巨大出力・
manifest不一致・トラバーサル名・exit 0でJSON無し)を、検証器とランナーの回帰テストとして常備する。
ランナー自身にも「禁止操作を自分で試みて `PermissionError` になることを確かめる」
セルフテストを持たせ、doctor から定期実行する。

### D-10. 更新・無効化・削除・ロールバック(確定・実装済み)

**決定**: 2026-08-31、依頼者が下の推奨をそのまま採用(「つぎいこう」)。同日に実装した。
**実装**: `toolpack_install.py --update` / `toolpack_manage.py`(list・disable・enable・
rollback・remove・purge)/ `toolpack_store` の版操作。実機で3件を入れ替えて確認済み(5-21)。

きっかけ: `excel_compare_chart` を直したあと、受入検査が工程2(名前の衝突)で止まり、
入れ替えるのに手作業の削除が要った(2026-08-31)。

#### 前提(すでにコードで確定している事実)

- **`registry.json` の `active_version` だけが有効化スイッチ**(D-3)。
  ディレクトリの存在は有効を意味しない
- `installed/<id>/<version>/{package,generated}` は**版ごとに残る**
- registry の書き換えは一時ファイル + `os.replace` で**原子的**
- 削除APIは実機で往復確認済み(5-3・5-16)
- **孤立版は自動削除しない**(doctor が報告するだけ。D-3)
- ハブは `discover()` のたびに registry を読み直す(サービス再起動が要らない)

#### 確定1: 追加と更新を別の操作にする

- 更新は「registry に同じ `id` があり、**版が違う**」ときだけ通す
- **版が同じで中身が違うものは拒否する**(`package_hash` で判定)。版を上げさせる。
  同じ版名で中身が変わると、どれが動いているか誰にも分からなくなる
- 検査(工程1)・単体テスト(工程3)・サンプル実行(工程4)は**追加とまったく同じもの**を通す。
  更新だからといって検査を省かない

#### 確定2: 切り替えは最後の1回だけ、原子的に行う

- 新版を `installed/<id>/<新版>/` へ**完全に用意し終わるまで、旧版は動いたまま**
- 最後に registry の `active_version` を差し替える(一時ファイル + `os.replace`)
- 途中で失敗したら**新版のディレクトリを消すだけ**で元に戻る。
  利用者から見て停止している時間が無い

#### 確定3: Open WebUI 側は「先に registry、後に Pipe」

Pipe は `tool.json` の宣言(表示名・受け入れ形式・依頼例)を持っているので、
宣言が変わったら貼り直しが要る。順序には理由がある。

| 順序 | 起きること |
|---|---|
| registry → Pipe(**推奨**) | 一瞬だけ「新しい形式をまだ受け付けない」。**壊れない** |
| Pipe → registry | 新形式を受け付けるPipeが**古い版へ流れる**。利用者にはエラーに見える |

- Pipe の貼り直しに失敗したら `active_version` を戻す(推奨2の逆操作)

#### 確定4: 前の版へ戻すのは、切り替えを逆へ回すだけ

- 版ごとの `generated/` が残っているので、**貼り直すPipeも既に手元にある**
- 承認は版ごとに記録する(D-14)。戻した先が未承認なら表示は `【未承認】` へ戻る。
  **承認を版から版へ持ち回さない**

#### 確定5: 無効化と削除は、同じ道の長さ違い

| 操作 | Open WebUI | registry | ファイル |
|---|---|---|---|
| 無効化 | Function・モデル設定を消す | `enabled: false`(版は保持) | 残す |
| 有効化 | 版別 `generated/` から貼り直す | `enabled: true` | — |
| 削除 | Function・モデル設定を消す | 項目ごと外す | **残す**(doctor が「登録の無い残置」として報告) |
| 実体の削除 | 無いことを再確認 | 登録が無いことを再確認 | **別操作**。「保存済みのツール」でチェック・確認後に削除(第0章) |

- 無効化でモデル一覧から消えるのが、利用者にとって一番分かりやすい。
  「一覧に残っているが動かない」は問い合わせを増やす
- **ファイルを即座に消さない**のは D-17(外部バックアップ)が未決だから。
  消したら戻せない。「孤立版を自動削除しない」(D-3)と同じ理由である

#### 確定6: 版は全部残す。自動で消さない

doctor は「使われていない版が N 個ある」と報告するだけで、自動では消さない。
依頼者が明示選択・確認した未登録ツールは、保存一覧から全保存版を完全削除できる(第0章)。

#### 実装で決めた細部

- **無効化・削除で残した版を「残置」と報告しない。**
  `orphan_versions()` は**台帳に載っていない**ディレクトリだけを列挙する。
  意図して残した旧版まで残置扱いすると、本当の取りこぼしが埋もれる。
  台帳に載っているが動いていない版は `retained_versions()`(戻せる版の一覧)
- **無効化は台帳を先に止める。** Open WebUI から外せなかったら台帳を元へ戻す。
  片側だけ止まった状態を作らない
- **更新の取り消しで既存を削除しない**(`_rollback_update`)。
  有効版を旧版へ戻し、旧版の生成Pipeを**上書きで**貼り直す。
  ここで `remove_pipe_completely` を呼ぶと、直そうとして本番を落とすことになる

#### 未決(企画課に確認が要る。実装は止めていない)

- **更新したとき、承認済みだったツールの承認をどう扱うか。**
  **依頼者の判断で「版ごとなので新版は未承認から」と確定**(2026-09-02)。
  ただし**小さな修正のたびに2名承認をやり直す運用が回るか**は企画課の判断による。
  承認済みは入れ替えられない(D-15)ため、誤字1つ直すのに
  「2人で取消 → 更新 → 2人で承認」の4手が要る。
  回らなければ `approval_policy.json` で人数を1人へ下げる
- **自動でファイル実体を消す条件。** 未決であり自動削除はしない。
  明示削除はGUIの保存一覧または `purge --yes` で実装済み(2026-09-07・第0章)。

**画面(最小)**

1. **一覧** — **1行 = Open WebUI に登録されているモデル1つ**(2026-09-01 に確定)。
   利用者がモデル一覧で選ぶものと同じ粒度にする。
   そのモデルが使うツール(ハブの接続役)と残っている版は、**モデルの下へ1段下げて畳む**。
   行数はモデルの数どまりで、ツールや版では伸びない。

   ```
   モデル                          版      状態  承認     気になること
   ▶ 【未承認】Excel比較グラフ      1.1.0  有効  未承認
         ツール  excel_compare_chart 1.1.0 有効
         版      1.0.0             1.0.0  戻せる      ← 選んで「前の版へ戻す」
   ▶ Excel分析・科別分析シート        -    -     承認済み
         ツール  excel_read                有効
         ツール  excel_comment             有効
   ```

   - **承認されているかは列で見る。まとめ方には使わない。**
     並びは手を入れる必要があるもの(未承認)を上にする
   - もとからある本番モデルは**承認済みとして出す** — 既に運用で使われており、
     この仕組みの承認手続きの対象ではないため。出どころは権限の判定に使う(D-15)
   - **モデルでないものをモデルとして並べない。**
     `excel_read`・`excel_comment` は Excel分析が使うツールであってモデルではない。
     リポジトリにファイルがあるのに登録されていないものも、モデルではない。
     どちらも「気になること」として実行結果の欄へ出す
     (並べると「使えるモデル」に見えてしまう)
   - 無効にした追加ツールは Open WebUI に登録が無いが、**戻せるよう一覧に残す**
   - **もとからある正式モデルは明示して持つ**(2026-09-01・Codex指摘)。
     `tools/open*webui*.py` を全部「正式」とみなすと、登録していないものや
     **廃止したもの**まで承認済みとして扱う。実際 `transcription_refiner` は
     2026-08-14 に登録解除した「再登録しない」もので、誤って再登録されたときに
     「もとからある=承認済み」と出てはいけない。ここに無いものは**管理外**
   - **Open WebUI から表示名を取れないときはパッケージの表示名を使う**(同指摘)。
     無効にしている間や一時的に繋がらないときに、`decision_extract` のような
     内部IDを利用者へ見せない。承認状態から `【未承認】` を付けるところまで
     doctor と同じ判定を通す
   - **どの行を選んだかでできることを変える**(同指摘)。
     版の行では「前の版へ戻す」だけ、ツールの行では何もできない。
     戻すつもりで版を選んだまま「登録を外す」が押せると、モデルごと消える
   - **どのモデルもファイルの行を持つ**(2026-09-01)。
     もとからあるモデルはリポジトリのファイル、追加ツールは生成Pipeの場所。

### D-12. 認証状態の表現方法と正本の置き場所

**確定**: 2名承認(D-14)はOpen WebUIに概念が無いため、
**認証状態の正本は接続アプリ側の台帳**になる。Open WebUI側の設定は台帳から派生させる。

**「正常に動く」と「正式に承認されている」は別**(提案元: GPT)。
動作検査に合格していても、企画課が承認するまでは未承認である。
1つのモデルについて、少なくとも次を**別々に**持つ。

| 項目 | 例 |
|---|---|
| 承認区分 | 正式承認 / 個人作成・未承認 |
| 技術状態 | 正常 / 検査失敗 / 未検査 |
| 稼働状態 | 有効 / 無効 |
| 種別 | 既存 / 新規追加 / 既存からの派生 |
| バージョン | 1.0.0 |
| 所有者 | 経営企画課 / 個人名・部署 |
| 派生元 | Excelコメント正式版 1.2 |
| ハッシュ | 承認時から変更されていないか |

**強制すべきこと**(提案元: GPT):

- 持ち込んだモデルは**必ず「未承認」から始まる**
- **パッケージ内に「正式版です」と書いてあっても信用しない。**
  承認情報は `tool.json` に置かない。台帳だけが持つ
- 正式承認へ変えられるのは権限を持つ人だけ
- コード・ひな型・設定を変更したら未承認へ戻す(**D-14 で確定**:承認は版ごとなので、新しい版は必ず未承認から始まる)

**公開範囲は確定**: 正式モデルも未承認モデルも**全員に見せる**。未承認モデルも利用できる(2-3 を参照)。
したがって `access_control` による可視性の制御は、承認区分には**使わない**。
(試用グループなど別用途で将来使う可能性は残るが、この件では不要)

**承認はラベルである。** 見えなくする防御は置かない。
**その結果、「見分けが付くこと」が唯一の対策になる。**
見えなくする防御が無いので、表示だけで支える必要がある。
現状の「モデル名を変えるだけ」を強くするには、複数の手段を重ねる:

| 手段 | 実機で確認できた効き方(Open WebUI 0.9.6) | 扱い |
|---|---|---|
| モデル名の接頭辞(例: `【未承認】`) | モデル選択一覧で常時表示され、最も確実に目へ入る | **主表示の候補**。承認時に表示名を付け直す |
| `meta.description` の先頭へ注記 | 一覧では情報アイコンだけ。マウスを置いたときに説明文が出る | 補足には使えるが、これだけでは未承認を見分けられない |
| アイコン(`profile_image_url`)でバッジ | 一覧の各モデル名の左に丸いアイコンが常時出る。専用画像APIがある | 視覚的な補助に使える。画像が無い場合はOpen WebUIの既定アイコンになる |

**並び順も制御できる**。`MODEL_ORDER_LIST` に入れたモデルIDを先頭から指定順に並べ、
それ以外はモデル名順になる。設定の取得・更新は `/api/v1/configs/models` に存在する。
正式モデルを上へ置く運用に使えるが、実際に自動更新するかは未決。

**副作用として想定しておくこと**: 全員に見せる方針では、
個人製作が増えるほど**モデル一覧が長くなり、選びにくくなる**。
見分けの表示と並び順が、そのまま使い勝手を決める。

**必要なコア改修**: 台帳の承認状態から、**表示名の接頭辞と `meta.description` の注記を
機械的に付け直す**手順を持つ(承認された時点で `【未承認】` を外す、など)。
`access_control` は触らない。

**ずれの検出**: 管理画面から直接変えられるため、GUIは「台帳と現状の差」を出す必要がある
(doctor の `drifted` 検出と同じパターン)。台帳では正式なのに画面には `【未承認】` が
残っている、という食い違いはここで気づく。

### D-13. 設定だけのパッケージ(variant)を認めるか

**位置づけ**: これは**最適化案であって必須仕様ではない**。
処理を持つパッケージだけでも構想は成立する。

自然な形は両対応:
GPT等が**独立した処理**を作ったら通常のツールパッケージ、
**ひな型や文体だけ**が違うなら設定パッケージ。
仕組みは1つのまま、パッケージに2種類を許す。

| 種類 | 中身 | 検査 | 用途 |
|---|---|---|---|
| 処理を持つパッケージ | `main.py` あり | サンドボックス実行・静的検査・スモーク | 新しい業務ロジック |
| **設定だけのパッケージ** | `main.py` **なし**。`parent` + `config` のみ | **コードが無いため検査対象が激減** | ひな型違い・文体違い |

利用者から見た操作は同じ(フォルダを置いて「検査して追加」)。
インストーラの経路・台帳・承認フローも共通にできる。

**背景**: 「モデルをコピーして中身を変える」は**モデル単位の複製**であり、
コードの複製ではないため「経路ごとに結果が食い違う事故」には当たらない
(利用者が明示的に別モデルを選ぶため)。

**残る懸念**: コアの処理本体を直したとき、`main.py` を持つ複製側は直らない。
担当者がいない前提では、少しずつ違う古い複製が並ぶ状態になり得る。
設定だけのパッケージはこの問題を受けない。

**最大の落とし穴 — 共有資材を参照させてはいけない**(提案元: GPT):

派生版が正式版と**同じひな型・同じ設定ファイルを参照**していると、
**派生版をいじった結果が正式版にも及ぶ**。

このシステムでは実際に危険である。
`templates/gui/excel_comment_gui_template.xlsx` は
[excel_comment_build.py](../../tools/excel_comment_build.py) が読む**書式の正本**であり、共有されている。
派生版がこれを指したまま書き換えれば、正式版のコメント書式が変わる。

→ **派生版は設定・ひな型の複製を自分のディレクトリに持つ。共有資材への参照にしない。**
構造としては次のように分ける。

```
共通の処理エンジン(コア。1つだけ)
  ├─ 正式版のプロファイル(設定・ひな型)
  └─ 派生版のプロファイル(設定・ひな型)   ← 複製を持つ
```

複製するのは**処理コードではなくプロファイル**である。

**引っかかる点 — 合成ひな型の置き場が無い**:
[.gitignore](../../.gitignore) は `templates/` と `*.xlsx` `*.docx` をまとめて除外している。
機密を載せないための正しい設定だが、**合成ひな型も一緒に落ちる**。

ひな型付きの派生モデルを GitHub 経由でオンラインAIに作らせるなら、
**機密でない合成ひな型だけを置ける専用の場所**を将来用意する必要がある。選択肢:

- `.gitignore` に例外を作り、指定の場所だけ許す(バイナリがgitに載る)
- ひな型を**生成スクリプト**として置き、必要なときに作る(バイナリを載せない方針を維持)

後者が既存方針と整合するが、書式そのものを人がExcelで編集する用途とは相性が悪い。未決。

**昇格の経路**: 派生版で調整 → 企画課が確認 → 正式版の新バージョンとして昇格、
という流れも想定されている。昇格の扱いは D-10(更新)と合わせて決める。

### D-14. 2名承認のプロセス(確定・実装済み)

**確定**: 企画課内で2名以上の承認があれば正式なモデルとして扱う。

**位置づけ(重要)**: これは**運営上の取り決めであって、技術的な強制ではない**。
設定画面で数クリックする程度で足りる。承認プロセスを厳密に作り込まない。

**最小の実装**:

- 台帳に「承認者名 + 日時」を積む。2件たまったら認証済みへ切り替える
- 認証済みになったら、表示(名前の接頭辞・説明文の注記)を切り替える(D-12)。
  **公開範囲は変えない**。未承認でも全員が見て使える
- 状態は **未認証 / 認証済み** の2つでよい(承認が0名か1名かは台帳を見れば分かる)
- 同じ人が2回押しても1件として数える

~~**推奨(未決)**: 取消は1名でできるようにする(提案元: Claude)。~~
→ **採らなかった。** 依頼者の判断で**取消も承認と同じ人数**(既定2人)にした。
ただし**人数は設定で変えられる**ので、事故を止めるのに2人待つのが重いと分かれば
`approval_policy.json` で1人へ下げられる(2026-09-02 確定)。

**安く入れられて効くもの**: 承認時のパッケージのハッシュも一緒に記録しておくと、
後で中身が差し替わったときに「承認時と違う」と表示できる。
自動で認証を外すところまでやるかは未決。

**承認記録の置き場所**: `logs/` のPIIレス運用ログとは別に持つ。
「本文や氏名を運用ログへ残さない」は**処理対象のデータ**についての規約であり、
承認者名は業務上の決裁記録なので性質が違う。混ぜると片方を守るために片方が壊れる。

**記録する最小項目**: 承認状態(未承認 / 1人承認 / 正式承認)/ 承認者名 / 承認日時 /
対象モデルのバージョン。

**表示名との繋がり(既に実装済み)**: 表示すべき名前は registry の承認状態から決まり、
`doctor` の `check_toolpack_names` と5分ごとの見張り(`toolpack_name_guard`)が
食い違いを検知して戻す(5-17)。承認記録を足すときは、
**承認記録 → registry の状態 → あるべき表示名** の派生を1本に保つこと。
2か所から表示名が決まると、見張りが自分と喧嘩する。

**更新との関係(D-10)**: 承認は**版ごと**に記録するため、新しい版は未承認から始まり、
前の版へ戻せばその版の承認状態に戻る。承認を版から版へ持ち回さない。
**ただし、小さな修正のたびに2名承認をやり直す運用が回るかは企画課の判断による**(D-10 の未決)。

**既知の限界(承知のうえで受け入れる)**:
企画課が共用PCの同一Windowsアカウントを使っている場合、承認は「名前を選ぶだけ」になり、
本人確認にはならない。**これは運営上の区分なので許容する**。
本人確認が要るなら Windowsアカウントを分けるか、管理アプリ専用の承認者アカウントを持たせる
ことになるが、初期版では作らない。

**未決**: 作成者本人を2名のうち1名として数えてよいか(企画課の運用規則として確認する)。
これは**人の決まり**であり、コードは名前が別々かどうかしか見ない。

#### 実装(2026-09-02・確定)

**決定**: 依頼者が「取消も2人。**承認も取消も人数を変えられるように**」と判断。
更新したら承認はやり直し(版ごとなので新しい版は未承認から)も確認済み。

**持ち方**: `registry.json` の**版の記録**へ入れる。

```jsonc
"1.1.0": {
  "package_hash": "…", "installed_at": "…",
  "approved": false,                 // 決まった状態(読み手はこれだけ見る)
  "approvals":   [ {"name": "石田", "at": "…", "package_hash": "…"} ],
  "revocations": [ … ],
  "approval_history": [ {"event": "approved", "at": "…", "by": ["石田","山田"], …} ]
}
```

- **票が証拠、`approved` が決まった状態。** 読む側(`is_approved`)は状態だけ見るので、
  既存の読み手は変えずに済む。人数の判定は書く側だけが行う
- ツール単位の `status` は**有効版から導く控え**。有効版が変われば書き直す
- **版ごとの承認を使っている項目では、印の無い版は未承認**。
  ここでツール単位へ落ちると、承認済みツールへ足した新しい版が承認済みに見える
- 決まったら**反対側の票だけ**片付ける。決め手になった票は残す
  (誰で決まったかを見せる・巻き戻せるようにするため)

**人数の決まり**: `additional-tools/registry/approval_policy.json`(見本は
`tool-packages/approval_policy.example.json`)。無ければ **2人/2人・自由入力**。
**壊れたファイルで承認が緩くなってはいけない**ので、下限は1人とし、
直した点は必ず表示する。承認できる人を並べておけば選ぶだけで済み、
打ち間違いで別人として数えられる事故が減る。

**承認すると表示名が変わる。** `【未承認】` は生成Pipeが持っているので、
**台帳を変えるだけでは画面の名前は変わらない**。人数に届いた時点で
Pipeを作り直して貼り直し、3か所そろったと確かめてから成功にする(D-10 と同じ道)。
失敗したら**入れた票ごと**元へ戻す。

**人数を途中で変えたときの扱い(2026-09-02・レビュー指摘)**

確定は**投票のときにしか起きない**ため、人数を下げると詰まることがあった。
2人必要なときに1票入れたあと1人へ下げると、その1票で足りているのに未承認のまま止まり、
**入れた本人はもう押せない**(同じ人は1件として数えるため)。

- 押したときに**まず「もう届いている票」を確定させる**。新しい票は入れない
- **決まったものは設定変更で覆さない。** 人数を上げても承認済みは承認済み。
  黙って承認が外れるほうが危ない
- doctor が「届いたまま確定していない」を見つけて知らせる

**運用上の帰結(承知のうえで採る)**: 承認済みは入れ替えられない(D-15)ので、
承認済みツールの誤字を1つ直すのに「2人で取消 → 更新 → 2人で承認」の4手が要る。
回らなければ `approval_policy.json` で人数を1人へ下げられる。

### D-15. 一覧GUIの権限分離(確定・実装済み)

一覧管理GUIは、追加専用アプリより**危険な道具**になる。
追加専用なら最悪でも「追加できない」で済むが、一覧管理は
**既存の本番モデル(文章処理・Excel分析・ヘルプ)を無効化・削除できてしまう**。

**推奨(未決)**(提案元: Claude):

- **認証済みモデル**: GUIから無効化・削除**できない**(見るだけ)
- **非認証モデル**: 作成者と管理者が操作できる

**前提条件**: 一覧に「削除」を出すなら、5-3で確認したサーバーAPIを院内クライアントへ実装し、
Functionとモデル設定の両方を確実に消して再確認できることが先に要る。
→ **この前提は満たした**。`remove_pipe_completely` が Function とモデル設定の両方を消し、
再取得して消えたことを確かめる。実機で往復確認済み(5-16)。

**確定: 権限は「人」ではなく「対象」で分ける(2026-08-31・実装済み)**

| 対象 | GUIからできること |
|---|---|
| 認証済みモデル | 見るだけ |
| 管理外モデル(このアプリの外で登録されたもの) | 見るだけ。「管理外」と表示 |
| 未承認モデル(このアプリで追加したもの) | 無効化・削除・版の切り替え |

理由: 企画課が**共用Windowsアカウント**を使う場合、本人確認ができない(D-14の既知の限界)。
**できない本人確認を前提にした権限は、あるように見えて実際には無い。**
対象で分ければ、誰が操作しても本番モデル(文章処理・Excel分析・ヘルプ)は壊れない。

**未決**: 「作成者」を識別できない前提のままでよいか。
本人確認が要るなら、管理アプリ専用の利用者名を持たせることになる(D-14の議論と同じ)。

### D-16. ハブのLAN露出への対処(確定・実装済み)

**決定**: 2026-09-02。**折り返し(127.0.0.1)で待つ。** それだけで閉じられる。

長らく「`127.0.0.1` への変更は Open WebUI(コンテナ)からの接続を切るため
採れない」としてファイアウォールでの遮断を検討していたが、
**実測して誤りと分かった**(5-25)。Docker Desktop は `host.docker.internal` 宛てを
折り返しへ中継するため、コンテナからの要求はハブへ **127.0.0.1 として届く**。

- `start_local_services.py` の既定を `127.0.0.1` にした。
  広げるには `--host` を明示して渡す必要がある(**既定を広い側にしない**)
- ファイアウォールの規則は要らない。**待っていないものは届かない**。
  Docker のサブネットを追いかける必要も、それが変わったときに壊れる心配も無い
- doctor に `check_service_exposure` を追加。**自分のLAN側アドレスへ実際に繋いでみて**、
  繋がったら注意を出す(繋がらないのが正しい姿)

**残っている広すぎる許可**: Windowsファイアウォールに

## 5. 判明している事実(実コードで確認済み)

判断材料。事実なので選択の余地はない。

### 5-1. 生成Pipeは `tools/` 直下でないとデプロイできない

[open_webui_deploy.py](../../tools/open_webui_deploy.py) の `validate_target_path` は、
対象を**リポジトリの `tools/` 直下**かつ `open_webui_*.py` という名前に限定している。
専用領域から登録するなら、許可パスの拡張が要る。

### 5-2. doctor が「実体の無い登録」を警告する

[doctor.py](../../tools/doctor.py) の `registered_plugin_findings` は、
`tools/` に実体が見つからない登録を「リポジトリに実体の無い登録があります」と報告する。
専用領域へ Pipe を置くと、**追加のたびに doctor が鳴る**。追加ツール領域を認識させる追従が要る。

### 5-3. 削除APIは実機で往復を確認済み(2026-08-31に解消)

**当初の穴は塞がった。** クライアントへ削除を実装し、テスト専用IDの仮登録で
往復を実機確認した(本番モデルには触れていない)。結果:

- `POST /api/v1/models/model/delete`(本文 `{"id": ...}`)→ **受理され、再取得で消えた**
- `DELETE /api/v1/functions/id/{id}/delete` → **受理され、一覧から消えた**
- 本番3件(文章処理・Excel分析・使い方ヘルプ)は前後で不変

したがって、登録後に失敗したときのロールバックは**実際に成立する**。
実装では削除の応答ではなく**再取得の結果**で成否を判定している
(APIが成功を返しても残っていれば失敗として扱う)。

以下は当初の記録(経緯として残す)。
`ApiClient` が持っていたのは `list_entries` / `get_entry` / `create_entry` / `update_entry` /
`activate_function` / `get_model` / `upsert_model_meta` の7つで、**削除処理が無かった**。

稼働中の Open WebUI 0.9.6 の実装には次のAPIが存在することを確認していた。

- Function / Pipe本体: `DELETE /api/v1/functions/id/{id}/delete`
- モデル設定: `POST /api/v1/models/model/delete`、本文は `{"id": "<model_id>"}`

したがって「Open WebUIに削除手段が無い」のではなく、**院内側のAPIクライアントに未実装**なのが
現在の穴である。Functionとモデル設定は別々に消し、両方が消えたことを再取得で検証する必要がある。

- 既存Pipeの**更新**なら、事前に取得した `server_content` で戻せる
- **新規登録**は、登録後に確認で失敗しても消せない。モデル一覧に壊れたモデルが残る

追加ツールは常に新規登録なので、こちらが本番である。
「ロールバックしました」と表示しながら実際は残っている状態は、
「失敗を成功として扱わない」に直接反する。**上記2つの削除をクライアントへ実装する必要がある。**
本番モデルを使った削除試験は行わず、実装時は専用の仮登録だけで往復を検証する。

### 5-4. 管理APIキーは環境変数からも読まれる

`load_api_key` は環境変数 `OPEN_WEBUI_ADMIN_API_KEY` を**ファイルより先に**見る。
これがユーザー環境変数に設定されていると、ログオン時に自動起動するハブが継承し、
ハブが起動する子プロセスまで丸ごと継承する。**分離したつもりが分離できていない**状態になる。

→ 鍵はファイル(`%USERPROFILE%\.open-webui\admin_api_key.txt`)に置き、環境変数には設定しない。
doctor で「環境変数に鍵が入っていないか」を見るのが確実。

### 5-5. 現行の安全ランナーは追加ツール用としては穴がある

[safe_task_runner.py](../../tools/safe_task_runner.py) が拒否するのは
**ワークスペース内の** `.env` / `data/` / `templates/` だけで、拒否リスト方式である。
書いていない場所は読める。具体的に:

- `%USERPROFILE%\.open-webui\admin_api_key.txt`(**ワークスペース外なので素通し**)
- 別案件の `input/`、過去の `output/`
- ユーザーフォルダ内の認証情報
- `os.environ` の読み取りは**監査対象ですらない**(パスの許可リストでは塞げない)

鍵はファイルへ移すだけでは足りず、D-9 の一式(許可リスト・環境変数の最小化・プロセス分離)が要る。

### 5-6. ハブの自動検出は台帳の変更を反映しない

[hub.py](../../local_tool_bridge/hub.py) の `discover()` は
`pkgutil.iter_modules` + `importlib.import_module` で `connectors/` を走査し、
モジュールの `SPEC` 変数を読む。**新しいファイルを置く分にはサービス再起動なしで繋がる**が、
台帳を読む共通ローダを1枚置く方式にすると、そのモジュールは `sys.modules` にキャッシュされ、
**台帳を書き換えても反映されない**。毎回評価される形(関数)への小改修が要る。

また `discover()` はツール名の重複を errors に落とすだけで、**静かに繋がらない**。
名前衝突の検査が要る。

### 5-7. ハブは同時実行1件・タイムアウト1800秒

[app.py](../../local_tool_bridge/app.py) の `_RUN_LOCK` で同時実行は1件、
`SCRIPT_TIMEOUT_SECONDS` は1800秒。
接続アプリのスモーク実行は、利用者のジョブの裏で最大30分待つ可能性がある。
「ハブが処理中なら待つか中止か」を決め、稼働中フラグを見えるようにする必要がある。

### 5-8. 依存の許可リストは2ファイル+wheelhouse から作る

`requirements.txt`(fastapi / httpx / openpyxl / python-docx 等)と
`requirements-office.txt`(pandas / matplotlib / python-pptx / xlrd 等)は別物で、
後者はホストvenv専用。`wheelhouse-win/` が実際に入れられるものの正本である。
**許可リストは手書きせず、この3つから生成する**(手書きは必ず腐る)。

### 5-9. 実物テンプレートは GitHub から見えない

[.gitignore](../../.gitignore) が `templates/` と `*.xlsx` / `*.docx` / `input/*` を除外している。

### 5-14. 工程1〜3の実装で判明した実測(2026-08-31)

検証器・保存領域・専用ランナーを実装する過程で、実際に動かして確かめた事実。

**(a) Windows の `zipfile` はエントリ名の `\` を読み書きの両方で `/` へ正規化する。**
そのためバックスラッシュ入りのZIPを Python 側から再現できない。
D-2 のバックスラッシュ拒否は**他の実装が作ったZIPに対する多重防御**として残し、
検査そのものは名前検査関数の単体テストで担保している。

**(b) `ZipFile.writestr` は暗号化フラグを保持しない。**
そのため「暗号化エントリを拒否する」検査も、ZIPを作って通す経路では試験できない。
エントリ属性検査の関数を暗号化フラグ付き `ZipInfo` で直接呼ぶ単体テストで担保している。

**(c) venv の `Scripts\python.exe` はベース実体を子プロセスとして起動し直すリダイレクタである。**
ジョブオブジェクトの `ActiveProcessLimit=1` に抵触して起動そのものが失敗する
(「Unable to create process」/ 終了コード101)。
対処として `pyvenv.cfg` の `executable` からベース実体を解決し、
venv の `Lib\site-packages` を `PYTHONPATH` で渡すことで、
**1プロセスのまま venv 相当の依存を使う**。これで D-9 の「プロセス数1」を守れる。

**(d) matplotlib は追加ツール用ランナーの下で動く(実測: 約4秒で日本語ラベル入りPNGを生成)。**
ただし機構は次のとおりで、依存の宣言に影響する。

- システムフォント(`%SYSTEMROOT%\Fonts`)は読み取り許可リストの外にあり、
  Python 経由の読み取りは**監査フックが実際に拒否する**(実測)
- その結果、matplotlib に登録されたフォント41件のうち**システム領域由来は0件**で、
  実際に使われたのは `matplotlib-fontja` 同梱の `ipaexg.ttf`(site-packages 内=許可リスト内)
- したがって **日本語のグラフを描く追加ツールは `matplotlib-fontja` の宣言が必須**である
  (無いと日本語が豆腐になる)。requirements-office.txt の `matplotlib-fontja==1.1.0` は
  この経路で効いており、外せない

### 5-15. 工程4〜7の実装で判明した実測(2026-08-31)

**(a) ctypes は必ずプロトタイプを宣言する。** 64bit では宣言を省くとハンドルが
32bit へ切り詰められ、`CreateProcessAsUserW` が `WinError 6`(ハンドルが無効)で失敗する。
`argtypes` / `restype` を宣言したら通った。Windows APIを ctypes で呼ぶ箇所すべてに効く注意。

**(b) 監査フックの読み取り許可リストは、nul デバイスを塞ぐと pytest が動かない。**
pytest の出力捕捉が `os.devnull` を開くため、許可しないと
パッケージ同梱の単体テストを隔離実行できない。nul は中身を持たないので読み書きとも許可した。
**この緩和後も、ctypes 直呼び・Python経由の逸脱書き込みはどちらも止まる**ことを確認済み。

**(c) 段階1(監査フックのみ)では ctypes 直呼びの書き込みが実際に素通りする。**
段階2(低整合性)では同じコードを OS が拒否し、ファイルも作られない。
両方式を突き合わせて試験してあり、**段階2が「あれば良いもの」ではない**ことの実証になっている。

**(d) 低整合性でも openpyxl と matplotlib は動く。** 低整合性が縛るのは書き込みだけで、
site-packages からの import は通る(5-14(d) と整合)。

### 5-19. 8.3短縮名のジョブ領域で、許可した書き込みが拒否される(2026-08-31・実測)

隔離ランナーが書込可能領域を**文字列比較**で判定しているため、
ジョブ領域の名前が Windows の 8.3 短縮名(`C:\Users\KELCRE~1\...`)だと、
ツール側が `Path.resolve()` した長い形(利用者名を展開した形)と一致せず、
**許可したはずの領域への書き込みが `PermissionError` になる**。

実害: pytest は `basetemp` を `resolve()` するため、`tmp_path` を使う
パッケージ同梱テストが全部落ちる。受入検査は工程3(単体テスト)で止まり、
**そのパッケージは一切インストールできない**。
受入検査の作業領域が `additional-tools/staging`(D:配下の長い名前)だったため
これまで表に出ず、ランナーを直接使ったときに初めて現れた。

対処: `run_tool_package` でジョブ領域と差し替え入口を必ず `resolve()` して
長い形へ揃える。**判定を緩めるのではなく、渡す側を正規化する。**
失敗の向きは「許可したものを拒否する」側なので、
隔離が破られる方向の危険はない(短縮しても領域の外は領域の外のまま)。

### 5-20. 実物の文字起こしは全件 Word だった(2026-08-31・実データで判明)

- ランナーが**ジョブ直下へ複製**し、パッケージは `import toolpack_textio` で使う。

`.docx` `.pptx` `.xlsx` `.xlsm` `.xls`。

**読めない形式は黙って失敗させない。** 何の形式で・どうすれば読めるかを返す。
拡張子を付け替えたファイル(`.docx` を `.txt` にした等)も中身で見分ける。

必要なら、ネット接続のある環境でwheelを取得してUSBで持ち込む必要がある。

**この件が示すこと**: 5-18 と合わせて、同じ誤りを2度している。
どちらも「自分が用意した架空データでは通るが、実物では通らない」だった。
受入検査の見本は、**実物と同じ作り・実物と同じ形式**にすること。

### 5-24. 管理操作にはプロセス間ロックが要る(2026-09-01・レビュー指摘)

**「読む→変える→書く」の全体は原子的でない**。

同一スレッドで取り直しても待たされないため、
ふさがった状況の試験は別スレッド(実運用では別プロセス)から掴む必要がある。

## 7. 検査で保証できること・できないこと

### 7-1. 接続アプリが自分で観測でき、パッケージ側が偽装できないもの

1. 例外を出さずに終了したか
2. `outdir` の外へ書いていないか(実行時に強制)
3. 禁止された読み取り・子プロセス・通信をしなかったか(同上)
4. 標準出力が規定のJSON1行だけだったか
5. 返した `files` が実在し、`outdir` 内か
6. **入力ファイルのハッシュが実行前後で変わっていないか**
7. 既存システムのテストが全部通るか

### 7-2. 保証できないもの

**業務結果が正しいかどうか。**

パッケージに同梱されたテストも `tool.json` の期待値も、**書くのは作者(オンラインAI)自身**である。
`assert True` と書かれれば通る。7-1 で確認できるのは
「安全に動いたか」「規格どおり返したか」までである。

業務上の正しさは、

- 既知のサンプルと期待結果によるテスト
- **最終的には人の確認**

が要る。ここを機械検査で代替できると考えてはいけない。

### 7-3. 静的検査の限界

`getattr(__import__("o"+"s"), "system")` のような難読化で、AST による禁止API検査は抜けられる。
脅威モデルは「悪意ある攻撃者」ではなく
**「善意だが間違えるオンラインAI」と「改変に気付けない持ち込み」**に置く。
前者には静的検査+テスト+スモークで足り、後者にはハッシュ・台帳で対処する。
実効的な担保は静的検査ではなく **実行時の閉じ込め・配置先の限定・持ち込み経路の管理** である。
