# オフラインでのブランチ運用とバックアップ

Gitはもともとネットワークを使わない。ブランチ・マージ・履歴・差分・巻き戻しは
すべてこのPCの中で完結する。ネットが要るのはGitHub等への `push` / `clone` だけで、
このリポジトリにはもともと外部リモートが無い。**完全オフラインになっても
失われる機能は無い。**

足りないのは「Gitの機能」ではなく、その周りの4つ ―― 履歴の預け先、作業を分ける手順、
コミットの分け方、壊れたときに戻る道である。ここではその4つを決めている。

---

## 1. 履歴の預け先(GitHubの代わり)

| | |
|---|---|
| リモート名 | `local` |
| 実体 | `D:\offline-kit\git\minutes-pipeline.git`(bareリポジトリ) |
| 通信 | 無し。ただのフォルダ間コピーなのでオフラインで動く |

```powershell
git push local
```

`main` は `local/main` を追跡しているので、引数なしで送れる。タグを作った回だけ
`git push local --tags` も実行する。

送り忘れは `doctor.py` が「履歴のバックアップ」として出す(未送信5件以上で注意)。

> **注意**: `D:` は作業フォルダと同じドライブなので、ディスクそのものが壊れると
> 両方消える。本当に守るならUSB等をもう1つ登録し、同じ `push` を2回打つ。
> `git remote add usb E:\minutes-pipeline.git`

### 復旧のしかた

作業フォルダが壊れたら、預け先から作り直せる。

```powershell
git clone D:\offline-kit\git\minutes-pipeline.git D:\minutes-pipeline-restored
```

ただし復元されるのは**コミット済みの中身だけ**である。`data/` `templates/` `input/`
`output/` `.venv` `.env` はGit管理外なので戻らない。venvの再構築手順は AGENTS.md にある。
クローン直後は `git config core.hooksPath .githooks` を再設定する(フックは複製されない)。

## 2. 1作業 = 1ブランチ

```powershell
git switch -c help-pipe-timeout        # mainから生やす
# ここで作業して、区切りごとに commit(pre-commitがテストを回す)

git switch main
git diff main...help-pipe-timeout > output\review.diff   # レビュー材料
git merge --no-ff help-pipe-timeout
git branch -d help-pipe-timeout
git push local
```

**`--no-ff` を必ず付ける。** 付けないと履歴が一直線になり、「どこからどこまでが
1つの作業か」が消える。付けておけばマージコミットが1作業の区切りとして残り、
`git log --first-parent --oneline` で作業単位だけを一覧できる。GitHubのPRマージと同じ形である。

### なぜ worktree を使わないか

`git worktree` で別フォルダを作ると、そこには `.venv` が無い。すると
[.githooks/pre-commit](../../.githooks/pre-commit) が「venvが見つからない」と判断して
**テストをスキップしたままコミットを通す**。柵が外れるので使わない。

`git switch` なら、`.venv` `data/` `templates/` `input/` `output/` はすべて
`.gitignore` 済みでブランチをまたいで残る。切り替えは一瞬で、環境は壊れない。

### 切り替えたらサービスを再起動する

ローカルサービスはこのフォルダのコードを直接読んでいる。ブランチを動かしたら
足元のコードが入れ替わるので、必ず再起動する。

```powershell
Stop-ScheduledTask -TaskName minutes-pipeline-local-services; Start-ScheduledTask -TaskName minutes-pipeline-local-services
```

Open WebUI に登録済みのPipe/Toolは登録時点のコピーなので影響を受けない。反映したい
場合だけ `open_webui_deploy.py --apply` を打ち直す。

### 切り替える前に作業ツリーを空にする

未コミットの変更を抱えたままブランチを動かすと、その変更が移動先まで付いてくる。
`git status` がきれいなことを確認してから切り替える。途中で置いておきたいだけなら
`git stash` ではなく、作業ブランチへコミットしておくほうが後から追える。

## 3. コミットは1つの目的で切る

**戻せる最小単位はコミットそのものである。** 復旧手段を `git revert` に据えている以上、
1つのコミットに3つの目的が混ざっていれば、1つを戻すために残り2つも道連れになる。
コミットの粒度が、そのまま戻せる粒度になる。

### 分けるか、まとめるか

| 分ける | まとめる |
|---|---|
| 目的が違う(不具合修正と機能追加) | 実装と、そのテスト |
| 片方だけ戻したくなる可能性がある | 関数の追加と `02-map.md`・`AGENTS.md` の追従(フックが同じコミットを要求する) |
| 片方だけ人に見てもらいたい | 改名にともなう呼び出し元の機械的な一括修正 |

判断に迷ったら「これを1年後に戻したくなったとき、一緒に消えて困るものが
入っていないか」で決める。

### 分けるのは「後から」ではなく「作業中」

区切りがついたその場でコミットする。まとめて書いてから切り分けようとしてはいけない。

`git add -p` でファイルの中を分ける運用は、pre-commit の部分ステージ検査が止める。
同じファイルが staged と unstaged の両方にある状態を許すと、**テストした内容と
コミットされる内容が別物になる**ためである。止まるのが正しい。混ざってしまったら
フックの指示どおり `git stash push --keep-index` で作業ツリーをステージ内容へ揃え、
テストを通してからコミットする。

### この柵の限界を知っておく

フックが止めるのは**同じファイル**のずれだけである。ファイルAだけをコミットして
ファイルBの変更を置いておく形は通る。だがテストは作業ツリー全体で走るので、
その緑は「Bの変更込みで緑だった」という意味にしかならない。

ファイルをまたいで分けたいときは、Bを別ブランチへ退避するか、AとBが独立していて
Bを外しても壊れないことを自分で確かめる。自動では守られない。

## 4. 戻り方は4つある(危険度が違う)

| やりたいこと | コマンド | 作業ツリー |
|---|---|---|
| 過去の中身を**見る** | `git show <タグ>:<ファイル>` | 触らない |
| 過去の状態を**別の場所へ取り出す** | `git archive <タグ> -o old.zip` | 触らない |
| 過去の状態まで**打ち消す** | `git revert --no-commit <タグ>..HEAD` → `git commit` | 書き換わる(履歴は残る) |
| 過去の地点から**枝を生やす** | `git switch -c 検証用 <タグ>` | 書き換わる(mainは無傷) |
| ~~履歴ごと巻き戻す~~ | ~~`git reset --hard`~~ | **使わない。作業が消える** |

上から順に試す。見るだけで済む調査に、書き換わる手段を使わない。

### 戻る目印を先に打っておく

動作確認が取れた地点にタグを打つ。打っていなければ戻り先を特定するところから
始めることになる。

```powershell
git tag -a stable-2026-08-18 -m "ヘルプPipe修正まで動作確認済み"
git push local --tags
```

### 実際に戻すとき

まず何が変わったかを見て、**全部ではなく原因のコミットだけを戻せないか**を考える。

```powershell
git log --oneline stable-2026-08-18..HEAD
git diff stable-2026-08-18
git revert <原因のコミット>
```

全体を戻す必要があるときは範囲で打ち消す。

```powershell
git revert --no-commit stable-2026-08-18..HEAD
git commit -m "stable-2026-08-18 の状態へ戻す"
```

これでタグ時点と**中身が完全に一致**し、履歴は1件も消えない。2026-08-18に36コミット分で
実測し、競合なしで通ることと結果がタグ時点と一致することを確認している。

ただし「戻す」は、**その後に足したものも消える**という意味である。上の実測では
タグ時点に存在しなかった `tools/doctor.py` が消えた。全部戻す前に、原因のコミットだけを
戻す道が無いかを必ず先に検討する。

`git reset` と `git checkout` は使わない。作業そのものが消え、消えたことも履歴に残らない。

### 戻らないもの

- **未コミットの変更** — 履歴に無いので戻せない。作業の区切りでコミットしておく理由がこれ
- `data/` `templates/` `input/` `output/` `.venv` `.env` — Git管理外

### やらかしたときの最後の砦

```powershell
git reflog
```

HEADが動いた記録が既定で90日残る。`reset --hard` で消したつもりのコミットも、
ここに出ているハッシュから拾い直せる。**何かを消してしまったら、まずこれを見る。**

## 5. Kiloにどこまでやらせるか

| 作業 | 担当 | 理由 |
|---|---|---|
| `git status` / `diff` / `log` / `show` | Kilo(自動) | 読むだけ |
| `git add` / `git commit` | Kilo(確認あり) | 「コミットしといて」で動く。差分を1回承認する |
| `git switch -c <新ブランチ>` | Kilo(確認あり) | 作業ツリーを動かさない。HEADが新しい枝に移るだけ |
| `git push local` | Kilo(確認あり) | 預け先へ足すだけで、作業ツリーに影響しない |
| `git revert <コミット>` | Kilo(確認あり) | 戻す唯一の手段。承認画面で実際の差分を見てから通す。範囲で戻す形は特によく見る |
| `git switch <既存>` / `merge` / `branch -d` / `worktree` | **人のみ** | 作業ツリーとブランチ構成が動く。サービス再起動の判断も要る |
| `git reset` / `checkout` / `restore` / `clean` / `rebase` | **禁止** | 作業を消す。復旧手段が無い |

この割り当ては [kilo.jsonc](../../kilo.jsonc) の `permission.bash` が物理的に強制している。
プロンプトでの約束ではないので、ローカルLLMが忘れても破れない。

### レビューをKiloにやらせる

オフラインではPRのレビュー画面が無い。代わりに差分をファイルへ出し、ask または plan
エージェントに読ませる。読むだけなので危険がなく、Kiloの使いどころとして一番良い。

```powershell
git diff main...<ブランチ> > output\review.diff
```

そのうえで ask エージェントへ「output/review.diff をレビューして、危ない変更と
テストが足りていない箇所を挙げて」と頼む。

## 6. コミットが止まったとき

pre-commit フックは3つの理由でコミットを止める。いずれもメッセージに対処が出る。

| 止まる理由 | 対処 |
|---|---|
| ステージ内容と作業ツリーが食い違う | `git add <ファイル>` で揃えるか、`git stash push --keep-index` で作業ツリーをステージ内容へ揃える |
| ファイルを追加/削除したのにコードマップが未更新 | `.kilo/rules/02-map.md` と `AGENTS.md` の表を直し、同じコミットに含める |
| pytest が失敗した / `tools/` に構文エラー | テストを直す。フックを迂回しない |

`--no-verify` は使わない。この3つはオフラインで気づけなくなる事故を止めるための柵である。
